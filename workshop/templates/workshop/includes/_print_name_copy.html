{% comment %} ============================================================================ THE SAVED PDF'S NAME — onto the clipboard as Print is pressed. ============================================================================ ONE copy for every page that is saved as a PDF: the invoice, the estimate, All Invoices (which also draws one old bill on its own, and the warranty slip), the service history and a spare shop's printed report. It was four hand-kept copies of one handler, each promising to stay identical to the invoice's — the shape a rule drifts out of. See CLAUDE.md, "The saved PDF's name". A page needs two things: a `js-print` class on its Print button, and `js/sound.js` for the warning's tone (without it the warning still shows, silently). DO NOT DELETE THIS AS DEAD CODE. Nothing on screen changes when the copy works, and no Django test can execute it. WHY: document.title is the only lever a page has over a saved PDF's name. iOS ignores it (every PDF is filed as "Safari - at "), and Microsoft Print to PDF opens its Save dialog with the name box blank — so the name goes on the clipboard and the owner pastes it. SILENT WHEN IT WORKS — the owner's call: a message on every bill would be confirming what cannot surprise anyone. SAID WHEN IT FAILS, BEFORE THE PRINT BOX OPENS (2026-10-09, the owner's call). A failed copy leaves the LAST file's name on the clipboard, so a paste on iPhone names this bill after the previous car. The first build showed the warning after the print box opened, and the owner's own test showed it landing BEHIND Chrome's print box — on iPhone the print sheet covers the whole screen — so it was seen only after the paste it warns about. So the press is HELD until the copy answers, which takes milliseconds: * copied → the print box opens, exactly as before * refused, or no clipboard at all (plain unencrypted HTTP — serving the Floor tablet over the LAN would do it) → NO print box; one small amber line and the warning tone on a clear screen. Pressing Print again while the line shows prints straight away. * no answer in WAIT_MS → the print box opens anyway, without a word The line stays until it is tapped or Print is pressed again. Never on paper. CAPTURE, ON `document`, NEVER A LISTENER ON THE BUTTON — the only place that runs BEFORE the button's inline onclick, which is what lets it hold the press (stopPropagation keeps the onclick from firing) and open the print box itself once the copy has answered. The write is made synchronously inside the click, because iOS drops user activation if it is deferred. IT CAN NEVER MAKE PRINTING IMPOSSIBLE. If this script never ran, the inline onclick="window.print()" prints as it always did; a failed copy costs one more press; a copy that never answers prints after WAIT_MS. Checked in Chrome on the laptop; the print box opened from a promise a few milliseconds after the tap still needs one check on a real iPhone. The script carries no comments of its own on purpose: an inline script is SERVED, and the customer-document tests read the page — the traps CLAUDE.md records for a URL scheme or a retired heading written in a served comment. {% endcomment %}
